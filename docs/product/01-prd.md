## 1. 서비스와 팀

| 구분 | 내용 |
|---|---|
| 서비스 | 얼쑤 |
| 팀 | 에헤라디야 |
| 구성원 | 애셔, 루디, 바우, 피비, 주드, 곤 |
| 초기 범위 | 한국 소재 대학교의 국제학생과 한국 학생 |
| 핵심 경험 | 인증된 대학생이 주최하는 한국 문화·대학 생활 기반 대면 모임 |
| 제품 방향 | 웹은 MVP 호응도 확인, 앱은 서비스 심화 구축 |
| 운영 | 팀이 관리자 대시보드에서 심사·운영·정보 게시 |

**한국 문화와 대학 생활을 경험하기 위해 한국 대학에 온 국제학생이, 인증된 대학생의 대면 모임에서 한국 대학생 친구와 함께 더 깊이 경험할 기회를 만든다.** 한국 학생도 참여자이며, 국제학생과 한국 학생 모두 일반 회원으로 모임에 참여하거나 직접 주최할 수 있다. 호스트는 고정 회원 등급이 아니라 자신이 개설한 모임에서의 역할이다.

서비스 대상 대학은 한국 소재로 한정한다. 모임 장소까지 캠퍼스 안으로만 제한한다는 뜻은 아니다.

## 2. 플랫폼별 진입과 회원가입

| 구분 | 진입 흐름 |
|---|---|
| 앱 | 온보딩 안에서 로그인/가입 → 학교 메일 인증 → 프로필 작성 → 가입 완료 |
| 웹 | 홈에서 모임 탐색 → 참여 또는 생성 의도 → 미로그인이면 로그인/가입 → 학교 인증·프로필 완료 → 원래 작업으로 복귀 |

웹은 탐색 전에 가입을 강제하지 않는다. 참여·생성 의도를 보존하지만 로그인만으로 참가 신청이나 게시를 자동 실행하지 않는다. 복귀 후 사용자가 최종 동작을 확인한다. 기존 회원은 이미 완료한 학교 인증과 프로필을 반복하지 않는다.

로그인은 **Apple·Google 간편 로그인**, **학교 웹메일 주소와 비밀번호 로그인**을 지원한다. 학교 메일 인증은 회원가입 시 별도로 수행한다. Apple/Google 로그인 성공 자체가 학교 인증을 대신하지 않는다.

학교 이메일 수신 확인을 통해 인증한다. 대학명은 메일 정보로 자동 지정하며, 대학을 식별하지 못하면 검색해서 선택하게 한다. 임의의 일반 메일과 대학 선택만으로 학교 인증을 완료시키지 않는다. 미등록 도메인의 확인 절차는 추가 논의한다.

### 프로필

| 항목 | 입력 규칙 |
|---|---|
| 이름 | 필수 |
| 대학명 | 필수. 메일로 자동 지정, 식별 실패 시 검색·선택 |
| 국적 | 필수 선택 항목으로 해석. 선택 목록에서 국가 지정 |
| 제1언어·제2언어 | 각각 입력받되 제2언어는 ‘없음’ 선택 가능 |
| 성별 | 필수 선택: 남·여·others·none. none도 유효한 선택값 |
| 관심사 | 선택 |

시스템 UI는 한국어·영어만 지원한다. 프로필에서 선택 가능한 언어 목록이 두 언어로만 제한되는지는 별도로 결정한다. 필수 정보와 학교 인증을 완료하면 회원 프로필을 생성·완료한다. 미완료 인증 계정은 가입 이어하기만 가능한 상태로 관리하는 설계를 제안한다.

## 3. 홈·탐색·이벤트 정보

### 홈과 검색

홈 상단에는 팀이 광고·정보 등을 게시하는 **info card 패널**을 둔다. 관리자 대시보드에서 내용을 게시·관리한다.

검색 전에는 **최근 검색어, 인기 이벤트, 최근 이벤트**를 표시한다. 검색어를 입력하면 **이벤트명**에 해당하는 결과를 표시한다. 지역과 카테고리 필터를 함께 적용할 수 있다. 지역은 시 단위로 구분하고 화면에는 ‘서울’, ‘인천’, ‘포항’처럼 짧게 표시한다. 인기 순위 산정 방식과 최근 기준은 추가 논의한다.

### 카드와 상세의 정보 구분

| 노출 위치 | 정보·행동 |
|---|---|
| 이벤트 카드 | 썸네일, 호스트 이름·대학·국적, 카테고리, 이벤트명, 날짜, 장소·지도 연계, 한국인/외국인 각각의 모집 인원, 관심 하트, 신고, 모집 중/마감 상태 |
| 상세 추가 정보 | 모집 기간 및 마감 일시, 한국어/영어로 분리된 자유양식 설명, 공개·비공개 댓글, 참가와 상태별 행동 |

한국인 몇 명·외국인 몇 명을 호스트가 따로 정하고 사용자에게 보여준다. 그룹별 모집 현황 표시와 해당 그룹의 정원 제한을 설계에 반영한다. 한 그룹의 남는 자리를 다른 그룹에 자동 전환하는 정책은 확정하지 않는다.

상세의 비공개 댓글은 작성자와 호스트만 소통하는 기능이다. **웹에도 댓글은 존재하며 앱 채팅과 별개다.** 운영자의 신고 조사 목적 열람 범위는 별도 정책으로 정한다.

## 4. 생성·공개·폐기 안내

학교 메일 인증과 프로필 작성을 마친 일반 회원은 원하는 모임을 개설한다. 필수 내용과 일정·정원을 서버에서 검증하고, 등록 성공 시 즉시 `published`로 공개한다. 심사 대기·심사중·승인·거절·재심사 과정은 사용하지 않는다.

심사 때문에 수정·삭제를 잠그는 정책도 폐기한다. 다만 공개 후 수정·취소의 범위, 참가자가 있는 모임의 일정/장소/정원 변경, 변경 안내는 별도 운영 정책으로 합의해야 한다. 이번 구현에는 새 수정·삭제 API를 자동으로 추가하지 않는다.

신고와 운영 조치는 사후 관리로 유지한다. 이미 참여자가 있는 모임을 취소하거나 운영자가 숨길 때는 모임 식별 정보·사유·참여 기록을 유지하고 안내한다. 이 운영 조치의 구현은 후속 작업이다.

## 5. 앱 채팅

웹 MVP에는 채팅을 넣지 않는다. 앱 채팅 탭에서는 이벤트 리스트 → 해당 이벤트의 방 목록 → 방 입장 순서로 이동한다.

| 역할 | 접근하는 방 |
|---|---|
| 호스트 | 이벤트 전체 공지방 + 참여자별 개별 방 |
| 참여자 | 이벤트 전체 공지방 + 본인과 호스트의 방 |

다른 참여자의 개별 방은 보거나 접근할 수 없다. 채팅에서 호스트 신고 등을 할 수 있다. 전체 공지방은 **호스트만 공지를 작성하고 참여자는 읽기만 가능**하다. 개별 방에서는 호스트와 해당 참여자가 쌍방 채팅한다.

## 6. 마이 이벤트

| 분류 | 목록 선택 후 동작 |
|---|---|
| 참여했던 | 상세 이동. 기존 참여 버튼 자리를 ‘리뷰 작성하기’로 변경. 작성 후에는 ‘내 리뷰 보기’, 리뷰 수정·삭제 제공 |
| 참여할 | 앱은 이벤트 채팅의 방 목록으로 바로 이동. 참여 취소하기 제공. 웹은 채팅이 없어 상세·참여 상태로 이동 |
| 관심 | 상세 이벤트로 이동 |
| 주최한 | 등록 즉시 공개 상태·모집 상태 확인, 종료된 모임은 참가자 리뷰 확인 |

참여했던 모임의 기준(신청 후 종료/실제 출석)은 추가 논의한다. 취소자 리뷰, 리뷰 작성 기간, 삭제 후 재작성 가능 여부도 별도 정책으로 정한다. 폐기된 모임은 일반 상세 대신 사유 안내로 연결한다.

## 7. 마이와 관리자 대시보드

마이에는 프로필 수정, 언어 설정, 신고 목록, Contact, 로그아웃/탈퇴, 알림 설정, 정책/약관, 공지사항을 둔다.

관리자 대시보드는 공개 모임·모집 현황 모니터링, 신고 처리·사후 숨김/폐기와 사유 전달, 광고/정보 패널, 문의·공지를 관리한다. 게시 전 심사 큐·승인/거절 버튼은 없다. 운영자 권한·조치 이력·중복 조치 방지는 필요하다.

## 8. 추가 회의 필요 사항

가설 및 측정 계획, 출시 수용 조건, 범위 밖과 위험의 상세 내용은 PRD에 넣지 않고 회의 안건으로 유지한다. 세부 미결정 목록은 [결정 로그](06-decisions.md#추가-결정이-필요한-항목)에서 관리한다.

- MVP 가설·측정 행동·실험 기간·성공 판단 기준
- 웹/앱 출시 우선순위와 출시 수용 조건
- 프로필 언어 선택 범위
- 미등록 학교 이메일 처리, 기존 계정과 간편 로그인 연결·비밀번호 복구
- 국적별 정원 분류·국적 수정·취소·대기열·참가 승인 방식
- 인기 순위 기준, 지도 제공자, 한/영 설명 필수 여부
- 출석·리뷰 자격·기간·삭제 후 재작성, 종료/취소 후 채팅 접근
- 공개 모임 수정·취소 범위, 참가자 변경 안내
- 사후 신고 처리 기준·기한, 폐기 사유 전달 채널, 광고 게시 운영
- 개인정보·탈퇴·보관·신고 정책, 참가비·결제 등 범위 밖 기능

## 9. 구현 및 운영 방향

웹은 Next.js, 백엔드는 팀에 익숙한 Java·Spring Boot를 사용한다. 프론트와 백엔드는 별도 Git 저장소에서 관리하고 자동 배포한다. 개발과 운영은 별도 Oracle Cloud VM·PostgreSQL·R2 버킷·인증 설정으로 분리한다. 같은 환경의 API와 DB는 VM 자원 확인을 전제로 함께 운영하는 방향이다.

API Gateway를 도입하는 방향이며 Spring Cloud Gateway는 후보, 세부 서비스 분리는 미확정이다. 썸네일은 Spring Boot에서 검증·압축하고 Cloudflare R2에 저장한다. 웹 호스팅은 Vercel 무료 플랜 적합성을 확인하고, 맞지 않으면 Cloudflare Workers를 검토한다. 무료 자원 확보나 실제 배포를 완료했다는 의미는 아니다. 상세는 [기술 스택·배포](07-tech-stack.md)를 따른다.
